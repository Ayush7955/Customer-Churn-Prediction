# Customer Churn Predictor Project Report

## 1. Executive Summary

This project builds a customer churn prediction system for a subscription-style business using a synthetic dataset of 100,000 customer records. The goal is to predict whether a customer is likely to leave the service (churn) or remain active.

The solution combines:

- data preprocessing and feature engineering,
- model comparison across multiple classifiers,
- a Streamlit dashboard for interactive prediction and exploration,
- evaluation using standard classification metrics, especially ROC-AUC.

The project compares three models:

1. Logistic Regression
2. Random Forest Classifier
3. Neural Network (TensorFlow/Keras)

The app uses the model with the highest ROC-AUC score on the evaluation set and displays churn probabilities for a new customer.

---

## 2. Project Objective

The main objective is to estimate churn risk for individual customers using demographic and contract-related data, helping a business understand customer retention risk. The application provides both:

- a prediction view for a single customer,
- a comparison dashboard showing the performance of multiple models.

This is a practical machine learning project that demonstrates the full flow from dataset generation to model training and deployment as a lightweight interactive app.

---

## 3. Data Description

The dataset is generated by the script in `generate_data.py` and saved as `synthetic_customer_churn_100k.csv`.

### Dataset Structure

The dataset contains 100,000 rows and 9 columns:

- `CustomerID`
- `Age`
- `Gender`
- `Tenure`
- `MonthlyCharges`
- `TotalCharges`
- `Contract`
- `PaymentMethod`
- `Churn`

### Target Variable

- `Churn` is the target column and is encoded as:
  - `0` = customer stayed
  - `1` = customer churned

### Synthetic Data Characteristics

The data is synthetic, not real customer information. It is generated using a hidden probability rule that increases churn likelihood for customers with:

- month-to-month contracts,
- longer time since the start of service,
- higher monthly charges,
- electronic check payment methods,
- certain age patterns.

This makes the problem realistic enough for demonstration, while also giving a clear validation signal for the modeling pipeline.

## 5. Data Preprocessing and Feature Engineering

The preprocessing pipeline in `main.py` is designed to handle both numeric and categorical features correctly.

### Numeric Features

- `Age`
- `Tenure`
- `MonthlyCharges`
- `TotalCharges`

These are processed with:

- median imputation for missing values,
- StandardScaler for feature normalization.

### Categorical Features

- `Gender`
- `Contract`
- `PaymentMethod`

These are processed with:

- most-frequent imputation,
- one-hot encoding using `OneHotEncoder`.

### Design Decision

The preprocessing is fitted only on the training data to avoid data leakage. This is a standard and important practice in machine learning workflows.

---

## 6. Modeling Strategy

The project trains and evaluates three models on the same processed dataset.

### 6.1 Logistic Regression

This is a strong baseline model for binary classification. It is fast, interpretable, and works well for linear decision boundaries.

### 6.2 Random Forest Classifier

The random forest model is configured with 200 trees and a minimum leaf sample constraint to reduce overfitting. It captures non-linear patterns in the data and is often effective for tabular customer datasets.

### 6.3 Neural Network

The neural network is built with Keras and includes:

- input layer matching the encoded feature dimension,
- Dense(64, ReLU),
- Dropout(0.3),
- Dense(32, ReLU),
- Dropout(0.2),
- Dense(1, Sigmoid)

It uses:

- binary cross-entropy loss,
- Adam optimizer,
- early stopping with validation monitoring.

---

## 7. Evaluation Methodology

The project uses an 80/20 stratified train-test split to preserve the churn class distribution. This ensures that the evaluation reflects the original class balance.

### Metrics Used

The models are compared according to:

- Accuracy
- Precision
- Recall
- F1-score
- ROC-AUC

### Why ROC-AUC Matters

Because churn prediction often requires balancing false positives and false negatives, ROC-AUC is a particularly relevant metric. It measures how well the model ranks positive cases above negative cases across different thresholds.

The project selects the model with the highest ROC-AUC score as the main model for the app’s prediction interface.

---

## 8. Results and Interpretation

The data pipeline calculates the model probabilities for the test set and then compares each model’s performance. The app exposes the results in a table and a ROC curve plot.

### Reported Model Behavior

The system is designed to support decision-making by showing the churn probability of a customer and a risk threshold. A lower threshold means more customers are flagged as high-risk, which increases recall at the cost of more false positives.

### Practical Interpretation

This is useful in a business setting where the objective may be to:

- prioritize retention offers for customers with the highest churn probability,
- reduce customer churn by targeting at-risk segments,
- identify patterns such as contract type or payment method affecting retention.

## 12. Limitations

This is a synthetic dataset and therefore has important limitations:

- it does not represent real-world customer behavior,
- relationships may be artificially simplified,
- performance metrics reflect the synthetic generation rule rather than real business data,
- the neural network and random forest may not generalize to real operational conditions without real-world retraining.

For real deployment, the system should be retrained using historical data from the actual business environment.
